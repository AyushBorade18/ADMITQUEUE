# AdmitQueue - CAP admission management (Next.js + Supabase + C++ engine)

A learning/demo system for the admission-cell workflow of a CAP-style engineering admission process:
**students log in with their CAP ID and password, and their saved admission details appear automatically**;
staff verify documents, run a service desk queue, plan appointments and run an allotment simulation.
The data-structure work (FODS) is done by a real **C++17 engine** that the website calls as a subprocess.

> **This is an independent project. It is not connected to the CET Cell, does not fetch real records from a CAP ID
> and does not use any real student data.** All 500 demo records are fictional and generated by a fixed seed.

## What is in here

| Part | Technology | Where |
|---|---|---|
| Website, API, protected pages, PWA | Next.js 16 (App Router), React 19, TypeScript, Bootstrap 5 | `src/` |
| Login/registration/sessions | Supabase Auth (cookie sessions through `@supabase/ssr`) | `src/lib/auth`, `src/app/api/auth` |

| Algorithms and data structures | C++17 executable (`admitqueue_engine`) | `engine/` |
| Seed, admin bootstrap, migrations | `tsx` scripts | `scripts/` |
| Tests | vitest + C++ test programs | `tests/`, `engine/tests/` |

## The CAP ID login flow (what the code does)

1. The browser sends **CAP ID + password** only.
2. The server normalizes the CAP ID (`dm26-000001` becomes `DM26000001`) and rate-limits the attempt (per IP and per ID, stored in PostgreSQL).
3. The server looks the ID up in its own table `student_login_ids` (secret key, server only) and finds the Auth account.
4. Supabase Auth checks the password. The student's e-mail is used only inside the server and is **never returned** to the browser.
5. A cookie session is set (HttpOnly). The user id always comes from the verified session, never from the request.
6. The server reads the student's profile, workspace, preferences, documents, history and linked CAP record **with the student's own session**, so PostgreSQL Row Level Security guarantees only their own rows come back.
7. The dashboard shows everything that is stored. The student is never asked to type details again.

Wrong password and unknown CAP ID give the same message and similar timing.

### Registration cases

| Case | Condition | Result |
|---|---|---|
| A | CAP ID matches a seeded fictional record and `DEMO_MODE=true` | Atomically linked (no double claim) |
| B | CAP ID not in the database | Account + workspace created, dashboard says admission details are not available yet |
| C | Record exists and `DEMO_MODE=false` (or the record is not fictional) | Staff approval request; nothing from the record is shown until approved |

With e-mail confirmation switched on in Supabase, registration says "check your e-mail" and login is refused until the address is confirmed.

## Quick start (details in SETUP_FROM_ZERO.md)

```bash
npm install
cp .env.example .env.local        # fill in your Supabase values
npm run db:migrate                # or paste supabase/migrations/*.sql into the Supabase SQL editor
npm run build:engine              # compiles the C++ engine (needs g++)
npm run db:seed                   # 500 fictional records, safe to repeat
npm run admin:bootstrap           # creates the admin from ADMIN_* variables
npm run dev                       # http://localhost:3000
```

Useful scripts: `npm run test:engine` (C++ tests), `npm run typecheck`, `npm run lint`, `npm test` (unit tests),
`npm run test:db`, `npm run test:e2e`, `npm run db:reset-demo`.

## Replacing the data source

All reads of admission records go through `src/lib/records/source.ts` (`CapRecordSource`). Today the source is the
`cap_records` table in your own Supabase database. If you are ever **authorised** to receive data from the CET Cell
(an official API, or a dataset you are legally allowed to hold), write one more class that implements the interface
and return it from `getRecordSource()`; or import the data into `cap_records` (CSV import on the admin "CAP records"
page). Do not load real personal data until you have the authority, a privacy notice, and set `DEMO_MODE=false`.

## Security notes

* Row Level Security is on for every table; the browser roles have only the grants they need (see `..._security.sql`).
* The Supabase **secret key** is used only in server code (`import 'server-only'`) and never sent to the browser.
* Admin accounts cannot be created by registration; the `role` column is only ever set by `npm run admin:bootstrap` or SQL you run yourself.
* Same-origin check on every write route, generic error messages, request size limits, zod validation.
* The engine process is started without a shell and with an empty environment, with a timeout and size limits.

## PWA

Installable (manifest + service worker + icons). The service worker caches only static files and a small
offline page. It never caches `/api/*`, `/auth/*` or any logged-in page, so private data is not stored by it.
Offline, the app shows an honest offline page; logging in, saving and all engine features need a connection.

## Honest status of testing

See the final report that came with this project for exactly what was run and what was not. In short: C++ tests,
database/RLS tests, unit tests and end-to-end tests of the production build were run **against a local PostgreSQL and
a Supabase emulator**; nothing was run against a real Supabase project, a real e-mail provider or Render.
